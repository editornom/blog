Q1: eBPF 기술이란 무엇이며 왜 혁명적이라고 평가받나요?
A1: eBPF는 리눅스 커널을 수정하거나 재컴파일하지 않고도 커널 내부에서 안전하게 프로그램을 실행할 수 있게 해주는 기술입니다. 정적이었던 커널을 프로그래밍 가능한 동적 환경으로 바꾸었다는 점에서 인프라의 패러다임을 바꾼 혁명으로 평가받습니다.

Q2: 과거의 BPF와 현대의 eBPF는 어떤 차이가 있나요?
A2: 1992년의 BPF가 단순한 네트워크 패킷 필터링 도구였다면, 2014년 진화한 eBPF는 64비트 레지스터와 상태 저장 구조인 Maps를 갖춘 커널 내 범용 가상 머신입니다. 이제는 시스템 콜, 보안, 함수 추적 등 시스템 전반을 제어할 수 있습니다.

Q3: eBPF가 제공하는 제로 터치 가시성의 장점은 무엇인가요?
A3: 애플리케이션 코드를 수정하거나 별도의 SDK를 심지 않고도 시스템 전체의 흐름을 관찰할 수 있다는 점입니다. 사이드카 에이전트 없이도 인프라 수준에서 발생하는 모든 이벤트를 실시간으로 파악할 수 있어 운영 편의성이 매우 높습니다.

Q4: 커널 수준에서 프로그램을 실행할 때 안전성은 어떻게 보장되나요?
A4: 리눅스 커널 내부에 있는 검증기가 코드를 실행하기 전 미리 검사합니다. 무한 루프에 빠지지는 않는지, 허용되지 않은 메모리 영역에 접근하지 않는지 꼼꼼하게 확인하여 eBPF 프로그램이 시스템 전체를 붕괴시키지 않도록 사전에 차단합니다.

Q5: eBPF 프로그램이 데이터를 저장하고 사용자 공간과 통신하는 방법은 무엇인가요?
A5: Maps라고 불리는 효율적인 공유 메모리 구조를 사용합니다. 이를 통해 커널 공간에서 수집한 데이터를 상태 정보로 저장하거나 사용자 공간의 제어 프로그램과 실시간으로 데이터를 주고받으며 복잡한 로직을 수행할 수 있습니다.

Q6: eBPF 활용 시 언급되는 시맨틱 갭이란 구체적으로 무엇을 의미하나요?
A6: 커널이 보는 시스템 지표와 개발자가 보는 비즈니스 문맥 사이의 단절을 뜻합니다. eBPF는 특정 프로세스의 I/O 발생은 알 수 있지만, 그것이 어떤 사용자 ID의 요청인지 혹은 어떤 주문 건 때문인지와 같은 상세한 서비스 정보는 파악하지 못합니다.

Q7: 실무에서 eBPF 프로그램을 직접 개발할 때 겪는 기술적 장벽은 무엇인가요?
A7: 검증기의 엄격한 제약 조건을 통과하는 것이 가장 어렵습니다. 스택 크기가 512바이트로 제한되고 복잡한 루프 구현이 까다롭기 때문에, 단순한 로직조차 커널에 대한 깊은 이해 없이는 구현과 로드에 실패할 확률이 매우 높습니다.

Q8: 다양한 리눅스 커널 환경에서 eBPF의 이식성 문제는 어떻게 해결하나요?
A8: 과거에는 커널 버전마다 재컴파일이 필요했지만, 현재는 BTF와 CO-RE 기술을 통해 해결합니다. 이를 활용하면 한 번 작성하고 컴파일한 eBPF 프로그램을 서로 다른 버전의 커널을 가진 수많은 노드에서 수정 없이 실행할 수 있습니다.

Q9: eBPF를 쓰면 코드를 안 고쳐도 다 보인다는데 그럼 오픈텔레메트리 같은 도구는 이제 안 써도 되는 건가요?
A9: 아니요, 두 기술은 함께 쓸 때 가장 효과적입니다. eBPF는 인프라 전반을 넓게 보여주지만 비즈니스 맥락이 부족하고, OpenTelemetry는 코드 안의 깊은 문맥을 보여줍니다. 따라서 전체 시스템을 입체적으로 보려면 두 도구를 통합해 사용하는 것이 좋습니다.

Q10: 우리 서버 커널 버전이 좀 낮은데 eBPF를 도입하면 시스템이 느려지거나 갑자기 뻗어버릴 위험은 없을까요?
A10: eBPF는 JIT 컴파일을 통해 매우 빠르게 실행되며, 검증기가 위험한 코드를 미리 걸러내므로 커널을 직접 수정하는 것보다 훨씬 안전합니다. 다만 최신 기능을 온전히 쓰려면 4.18 버전 이상의 커널을 권장하며, 도입 전 호환성 확인은 필수입니다.
