Q1: eBPF란 무엇인가요?
A1: 리눅스 커널을 수정하거나 재부팅하지 않고도 커널 내부에서 안전하게 사용자 정의 프로그램을 실행할 수 있게 해주는 기술입니다. 커널 기능을 확장할 수 있는 유연한 프로그래밍 인터페이스 역할을 합니다.

Q2: eBPF의 핵심 작동 원리는 무엇인가요?
A2: 작성된 코드는 검증기(Verifier)를 통해 안전성을 확인받은 뒤, JIT 컴파일러를 거쳐 네이티브 기계어로 변환되어 커널 내 샌드박스 환경에서 고성능으로 실행됩니다.

Q3: 이 기술이 왜 중요한가요?
A3: 기존 방식과 달리 애플리케이션 코드를 수정하지 않고도 시스템 전체의 가시성을 확보할 수 있기 때문입니다. 특히 복잡한 마이크로서비스 환경에서 성능 저하 없이 모니터링이 가능하다는 점이 강점입니다.

Q4: 검증기(Verifier)는 어떤 역할을 하나요?
A4: 커널 내에서 실행될 프로그램이 시스템을 멈추게 하거나 무한 루프에 빠지지 않는지, 잘못된 메모리 주소에 접근하지 않는지 등을 정적으로 분석하여 전체 시스템의 안정성을 보호합니다.

Q5: CO-RE 기술이란 무엇인가요?
A5: Compile Once, Run Everywhere의 약자로, 특정 커널 버전에 종속되지 않고 다양한 환경에서 수정 없이 eBPF 프로그램을 실행할 수 있게 해주는 이식성 강화 기술을 의미합니다.

Q6: 기존의 에이전트 기반 모니터링 방식과 어떤 차이가 있나요?
A6: 기존 방식은 사용자 공간으로 데이터를 복사하는 과정에서 성능 부하가 크지만, eBPF는 커널 내에서 데이터를 직접 처리하거나 필요한 정보만 효율적으로 전달하여 오버헤드를 획기적으로 줄입니다.

Q7: 도입 시 운영 측면에서 고려해야 할 단점은 무엇인가요?
A7: 커널 구조에 대한 심도 있는 이해가 필요하며, C 언어의 제약 사항을 준수해야 하는 등 학습 곡선이 높습니다. 또한 문제가 생겼을 때 디버깅 과정이 일반 앱보다 훨씬 까다롭습니다.

Q8: eBPF를 사용할 때 발생할 수 있는 보안 리스크는 무엇인가요?
A8: 기술의 권한이 큰 만큼, 공격자가 시스템 권한을 얻어 악성 eBPF 프로그램을 주입할 경우 커널 수준에서 은밀하게 데이터를 탈취하거나 보안 도구를 우회하는 경로로 악용될 위험이 있습니다.

Q9: 쿠버네티스에 eBPF를 도입하면 사이드카 방식보다 성능이 진짜 좋아지나요?
A9: 네, 맞습니다. 사이드카 방식은 통신할 때마다 사용자 공간을 거치며 지연이 발생하지만, eBPF는 커널 레벨에서 네트워크 패킷을 직접 가로채 처리하기 때문에 자원 소모가 훨씬 적고 속도도 빠릅니다.

Q10: 리눅스 커널을 잘 모르는 개발자가 eBPF를 바로 실무에 쓸 수 있을까요?
A10: 솔직히 쉽지 않습니다. 엄격한 검증기 통과 조건이나 메모리 스택 크기 제한 같은 커널 특유의 제약을 이해해야 하므로, 실리엄이나 픽시 같은 완성된 도구를 먼저 활용하며 단계적으로 접근하는 것을 추천합니다.
