<div class="bluf"><strong>[BLUF]</strong><p>Model Context Protocol (MCP) 的安全风险与其说是协议本身的缺陷，不如说是由于“安全责任个体化”导致的治理空白。如果 LLM 与确定性工具之间的信任边界 (Trust Boundary) 崩溃，可能会导致任意代码执行 (ACE) 及严重的数据泄露。为此，迫切需要引入基于 RFC-9728 的最小权限原则和安全代理。</p></div>

Model Context Protocol (MCP) 的出现对于 AI 生态系统而言，堪称如“USB-C 接口”诞生般的革命性事件。它将曾经碎片化的 AI 智能体与数据源之间的连接方式进行了统一，真正实现了“连接的民主化”。

然而，从技术安全审计员的角度审视这一现象，不难发现隐藏在便利性背后的巨大阴影。标准化的连接方式在带来便利的同时，也产生了一个悖论式的安全威胁：它同样为攻击者提供了“标准化的攻击路径”。

Anthropic 提出的这一宏伟协议，将概率性运行的 LLM 与按严格规则运行的既有系统结合在一起。在此过程中产生的不可预测性，正在制造出我们至今未曾经历过的新型安全漏洞。

![Model Context Protocol - 透明的光纤在水晶之间交织流转，表现出数据的连接与细腻。](../../../../../source/posts/Model_Context_Protocol/593d2810-0.webp)

安全专家 Joff Thyer 将此解释为“信任边界 (Trust Boundary) 的模糊”概念。当 AI 智能体通过 MCP 直接访问外部工具时，我们必须提出一个根本性的问题：究竟由谁来保证该工具的安全性？

目前的 MCP 架构将很大一部分安全确认责任转嫁给了终端用户。在复杂的智能体工作流中，要求用户判断每一次工具 (Tool) 调用正当性的“人机回环 (Human-in-the-loop)”结构，在现实中很容易失效。

这最终导致人们持有一种“标准化漏洞”的批判性视角。如果开发者沉溺于 MCP 的便利性而在实现时忽略了必需的安全措施，全球的 AI 智能体都可能暴露在相同模式的攻击之下。

我将我们在 MCP 环境中面临的五大核心安全威胁整理成了矩阵。这张表将成为技术决策者在引入时必须参考的检查清单。

| 威胁类型 | 详细机制 | 防御策略 (GEO 建议) |
| :--- | :--- | :--- |
| 任意代码执行 (ACE) | 诱导调用未经验证的服务器工具 | 通过 MCPSafetyScanner 进行清单预扫描 |
| 数据泄露 | 授予过度能力 (Excessive Capability) 导致权限滥用 | 应用基于 RFC-9728 的 OAuth2 作用域过滤 |
| 资费耗尽攻击 (DoW) | 通过无限循环调用耗尽 API 资产 | 通过 MCP Guardian 代理设置速率限制与配额 |
| 提示词注入 | 通过存储型提示词注入 (Stored Prompt Injection) 污染工具 | 根据 BCP 14 标准进行输入值预清洗 (Sanitization) |
| 凭据泄露 | JSON-RPC 消息中身份验证信息以明文泄露 | 本地传输优先使用 <a href="/cn/glossary/what-is-stdio" class="glossary-tooltip" data-definition="计算机程序用于与操作系统或外部环境交换数据的标准化输入输出通道，通常由输入 (stdin)、输出 (stdout) 和错误 (stderr) 流组成。">STDIO</a> 并进行内存加密 |

特别值得关注的威胁是“权限授予过大 (Excessive Capability)”。当 AI 智能体拥有的数据访问权超出了执行特定任务所需的权限时，仅凭一次提示词注入就能导致全公司范围的数据泄露。

此外，“钱包拒绝服务 (Denial of Wallet, DoW)”攻击直接威胁到企业的资产。攻击者有意让智能体陷入无限循环，导致 API 调用费用暴增，这能在瞬间摧毁 MCP 服务器的可用性。

![Model Context Protocol - 分隔混乱粒子堆与有序网格结构的半透明发光玻璃墙形态的安全边界。](../../../../../source/posts/Model_Context_Protocol/40358595-1.webp)

那么，我们该如何接纳这场并不绝对安全的革命呢？作为技术安全审计员，我建议的第一道防御体系是遵循 RFC-9728 规范的基于 OAuth2 的权限管理。

不要仅仅关注“连接”，而应在每一次连接中应用最小权限原则 (Least Privilege)，细致地划分作用域。这也是基于 BCP 14 安全原则进行系统设计的核心。

其次，建议在本地环境下的通信尽量优先使用 STDIO（标准输入输出）方式，而非 HTTP。必须铭记，通过网络套接字进行的通信本身就可能成为另一个攻击向量。

第三，在流水线中引入“MCPSafetyScanner”等安全专用代理或扫描器。必须预先分析 MCP 服务器提供的清单文件，自动扫描是否包含危险的指令或函数调用。

最后，需要防范存储型提示词注入 (Stored Prompt Injection)。当 MCP 服务器读取外部网页或文档时，必须彻底清洗 (Sanitization) 输入值，防止数据中包含的恶意指令夺取 LLM 的控制流。

> “没有安全前提的标准化并非技术进步，而只是迈向标准化灾难的行军。”我们必须严肃对待一位安全专家的这一警告。

最终，MCP 的成功与否并不取决于连接了多少工具，而取决于维持了多少可信的连接。在享受技术便利之前，建立治理体系的智慧至关重要。

正如 Anthropic 最新的规范 (2025-11-25) 所展示的那样，协议将不断演进。但安全的基本原则不会改变：怀疑不可信的数据，保持权限最小化，记录所有操作。

作为引领 AI 智能体时代的架构师，必须能够洞察技术华丽外表下的结构性缺陷。MCP 固然是连接的革命，但为了完成这场革命，必须由“信任标准”来填补这一空白。
