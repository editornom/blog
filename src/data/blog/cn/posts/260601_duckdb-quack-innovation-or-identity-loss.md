  a: "这是因为用户提出了访问远程服务器功能的需求，以便处理超出本地机器资源的超大规模数据集。DuckDB 对此做出了响应，选择了通用性和兼容性较高的基于 HTTP 的远程通信方式。"

- q: "文中指出的 DuckDB 身份危机意味着什么？"

<div class="bluf"><strong>[BLUF]</strong><p>DuckDB Quack 虽是尝试突破仅限本地引擎局限的努力，但远程网络延迟完全抵消了 DuckDB 核心的零拷贝性能优势。特别是 76GB CSV 基准测试，是一个忽略了实际使用 <a href="/cn/glossary/what-is-parquet" class="glossary-tooltip" data-definition="一种开源文件格式，按列（Column）而非行（Row）存储数据，优化了压缩效率和大规模数据分析处理速度。">Parquet</a> 编码效率的营销数值，且缺乏企业环境必需的安全架构。</p></div>

## 1. DuckDB 危险的尝试：“Quack”远程协议的出现

 ### 1.1. 本地分析之王，为何梦寐以求“服务器”？
 在数据工程生态系统中占据独特地位的 DuckDB 最近推出了名为“Quack”的远程协议。作为一个原本基于 <a href="/cn/glossary/zero-copy" class="glossary-tooltip" data-definition="一种不通过内存复制而直接访问数据以实现处理速度最大化的技术">Zero-Copy</a> 架构、将本地机器资源发挥到极致的引擎，这一变化被视为其技术身份的转折点。虽然官方给出的理由是用户为了处理更大的数据集而需要服务端-客户端模式，但这很可能是一场自毁嵌入式引擎本质优势的危险赌博。

 ### 1.2. Quack 协议的技术骨架：HTTP 与远程查询机制
 Quack 放弃了复杂的专用二进制协议，转而选择 HTTP 传输层，以此兼顾了通用性和与 DuckDB-Wasm 的兼容性。然而，这意味着它必须宿命般地承担数据传输过程中不可避免的 HTTP 开销和网络堆栈延迟。如果分析型数据库的首要价值是“性能”，那么这种设计选择是否能给习惯了本地执行速度的用户带来满意的体验，实在令人怀疑。

## 2. 矛盾的开始：自我否定零拷贝 (Zero-Copy) 的优势

 ### 2.1. 网络开销：吞噬向量化引擎速度的瓶颈
 支撑 DuckDB 超高速性能的核心技术无疑是 <a href="/cn/glossary/vectorized-execution" class="glossary-tooltip" data-definition="一种执行模型，它不是一次处理一个数据，而是以向量（数组）为单位进行批量处理，从而最大化 CPU 缓存效率">Vectorized Execution</a>。这种极大化 CPU 缓存效率的方式在本地内存中移动数据时大放异彩，但在通过 Quack 进行远程调用时，情况就完全不同了。数据被拆分为网络数据包并重新组装的过程中产生的无数次数据复制，成为了 DuckDB 极力想要避免的性能下降的元凶。

 ### 2.2. 基准测试的陷阱：76GB CSV 数据传输数值的真相与扭曲
 从技术角度来看，DuckDB 提供的基准测试数据带有浓厚的营销色彩。他们引以为傲的“76GB CSV 传输”数值，实际上是以分析环境中几乎不使用的低效格式为基准的。下面是从现代数据架构视角重新解读的性能对比表：

 | 比较项目 | DuckDB (Local) | DuckDB Quack (Remote) | PostgreSQL (Server) |
 | :--- | :--- | :--- | :--- |
 | **数据访问方式** | Zero-copy In-memory | HTTP Binary Streaming | Row-based Socket |
 | **主要开销** | 无 (CPU/缓存优化) | 网络延迟 (TCP) | 客户端-服务器握手 |
 | **安全机制** | OS 文件权限 | 简单 Token (认证函数) | 高级 RBAC / TLS |
 | **最大性能** | 磁盘 I/O 限制 | ~5 Gbps (网络受限) | 连接池受限 |

 ### 2.3. “嵌入式”本质优势稀释时产生的机会成本
 仔细审视基准测试数值，76GB 的 CSV 压缩成 Parquet 格式后不到 3GB，而在 4.94 秒内完成传输仅相当于约 4.85 Gbps 的带宽利用率。这在现代 10Gbps 以上的网络环境下绝不能被称为创新水平。相反，给人的印象是原本应投入到本地引擎优化的开发资源，正在被分散到不完全的服务端化开发中。

## 3. 准备不足的服务端化：安全与运维风险

 ### 3.1. 简单 Token 认证的局限：作为企业级数据栈的安全缺陷
 Quack 协议的安全政策远未达到企业环境所要求的水平。目前提供的通过 `quack_authentication_function` 进行的简单 Token 比对方式，与提供精细 RBAC（基于角色的访问控制）或详细审计日志的现有 DBMS 相比，是一个致命的弱点。将 DuckDB 作为对安全要求极高的企业级数据栈进行服务端化运行，无异于用薄木板挡住金库大门。

 ### 3.2. 并发控制与状态管理：重复 SQLite 走过的荆棘之路？
 我们还记得过去 SQLite 试图过度扩展为服务器数据库时所经历的无数并发问题。由于 DuckDB 也是被设计为单用户优化引擎，要完美解决通过 Quack 让多个客户端远程连接时产生的状态管理和锁 (Lock) 竞争问题并非易事。随着运维复杂度的增加，DuckDB 所拥有的“安装即运行的简单性”魅力将会消失。

 ![DuckDB Quack - 在半透明玻璃迷宫中寻找道路的一个金色光点，表现了嵌入式模型与服务器模型之间复杂的结构混乱。](../../../../../source/posts/DuckDB_Quack/24c103b3-1.webp)

 ### 3.3. DuckLake 与 Quack 结合引发的架构混乱
* **数据传输效率批判**：社区中有很多批评声音认为，忽略 Parquet 编码效率的 76GB CSV 基准测试扭曲了实际工程现场的情况。
* **安全配置的脆弱性**：官方设置的 Token 认证允许短至 4 个字符，这种结构极易受到暴力破解攻击。
* **批处理优化限制**：`quack_fetch_batch_chunks` 的默认值 12 会导致在高带宽环境下，网络速度跟不上向量化引擎的运算速度，从而产生瓶颈。
* **社区舆论**：专家组更希望 DuckDB 能够坚持本心，在分析速度上达到巅峰，而不是迷失身份去尝试成为第二个 PostgreSQL。

> "DuckDB 的真正价值在于无需复杂配置的简单性。Quack 正为了这种简单性，牺牲了原则去选择一条不完全的服务器之路。"

## 4. 结论：DuckDB 应当回归“最快本地引擎”

 ### 4.1. 在用户“便捷性”需求与技术“纯粹性”之间的妥协点
 所有的技术都会响应用户的需求而进化，但这种进化绝不应以蚕食自身核心优势为代价。Quack 协议以提供远程访问这一甜头为代价，损害了 DuckDB 积累的“零拷贝性能”这一技术纯粹性。真正的创新不在于网络的那一头，而在于如何更有效地榨取本地机器的 CPU 和内存。

 ### 4.2. 对 DuckDB 生态系统未来发展方向的建议
 DuckDB 不应试图与服务器市场的强大竞争者抗衡，而应专注于成为数据科学家本地沙盒中最强大的武器。希望 Quack 能作为一个针对特殊情况的实验性扩展，而非主流功能存在，并重新回归到单节点内压倒性的查询性能提升上。因为这正是我们热爱并选择 DuckDB 的真正原因。

> "网络协议和数据格式是两码事。为了远程传输而放弃列式格式的优势，无异于技术倒退。"
