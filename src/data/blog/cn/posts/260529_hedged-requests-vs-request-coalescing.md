- q: "什么是对冲请求（Hedged Requests）？"

  a: "当针对同一资源的多个请求同时进入时，将它们合并为一个请求进行处理。这通常用于减轻后端系统的负载，并最大化数据库或计算资源的效率。"

- q: "为什么在应用对冲请求时必须保证幂等性？"
  a: "因为会对相同的请求进行重复发送。如果 API 不具备幂等性，可能会导致重复支付或数据状态扭曲等致命的业务逻辑错误，风险极高。"

  a: "是指由于将大量请求合并为一个进行处理，当这唯一的处理过程失败或延迟时，所有关联的客户端都会同时遭遇故障的现象。这是为了效率而放弃独立性的结果。"

  a: "需要设置管理请求的内存队列阈值，并结合熔断器。当合并逻辑本身发生瓶颈或故障时，必须能够快速传播失败，以保持整个系统的响应能力。"

<div class="bluf"><strong>[BLUF]</strong><p>分布式系统优化技术 Hedged Requests（对冲请求）和 Request Coalescing（请求合并）是把双刃剑。设计不当的对冲机制可能演变为自杀式 DoS 攻击，而疏忽的请求合并则会导致单个请求失败波及所有客户端的“命运共享（Fate Sharing）”风险。因此，保证幂等性并结合熔断器是必不可少的策略。</p></div>

在分布式系统的世界中，延迟（Latency）即成本，架构师们为了降低延迟付出了巨大的努力。然而，我们深信不疑的优化技术，有时却会化作刺向系统心脏的匕首。

如果仅仅沉迷于改善性能指标，很容易忽略系统必须承受的运营风险本质。特别是在追求高可用性的现代微服务环境中，更需要一种精细化的方法。

在本次分析中，我们将深入探讨最近通过 Istio 或各种库普及的两种优化技术的阴暗面。让我们一起看看，优化是如何触及摧毁可用性的临界点的，并划清那条危险的界限。

## 分布式系统的双刃剑：Hedged Requests 与 Request Coalescing 的致命风险

为了提高系统响应速度而引入的技术，通常采用改变流量形态或重新分配资源效率的方式。在这一过程中，必然会产生新的失败点。

**Hedged Requests** 是为了防止响应变慢而多发送一个相同请求的方式，而 **Request Coalescing** 则是将相同的多个请求合并为一个进行处理的方式。从概念上讲，两者处于截然相反的位置。

然而，这两种技术都面临一个共同的风险：在试图解决“不可预测的延迟”时，可能会引发“不可预测的整体故障”。这就是为什么我们不能沉溺于优化的幻觉，从而过度自信地评估系统的基础能力。

## Hedged Requests：是解决 <a href="/cn/glossary/tail-latency" class="glossary-tooltip" data-definition="系统响应时间中处于前 1~5% 的长延迟时间。">Tail Latency</a>，还是自杀式流量攻击？

### Google 的“Tail at Scale”策略在现实中演变为 Self-DoS 的瞬间

Google 提出的“Tail at Scale”策略的核心——对冲（Hedging）非常有吸引力。当特定请求出现延迟时，向其他副本发送请求并使用最先到达的响应，这种方式能革新性地减少延迟。

但这只有在资源充足的情况下才是有效的魔法。当系统已经承受压力时，草率触发的对冲会将流量瞬间放大两倍甚至三倍，变成一场“自杀式 DoS 攻击”。

特别是如果由于疏忽设置了 Istio 的推测性重试（speculative retries），会导致向已经发生延迟的后端倾注更多请求，最终将整个系统推入无法恢复的泥潭。

### 缺乏 <a href="/cn/glossary/idempotent-api" class="glossary-tooltip" data-definition="即使多次执行相同的请求，结果也不会改变的 API 特性。">Idempotent API</a> 保证的对冲是数据完整性的定时炸弹

引入对冲时最容易忽略的一点就是数据的完整性。如果不能保证幂等性（即相同的请求发生两次，结果也必须相同），那么对冲应该被视为禁忌。

如果对支付请求或状态变更 API 应用了对冲，由于网络延迟导致两次请求都成功了，会发生什么？这不仅是简单的系统故障，更会直接导致业务层面的灾难。

归根结底，业务逻辑的稳固性应该优先于技术优化。不具备幂等性担保的对冲，无异于在架构中埋下了一颗不知何时会爆炸的定时炸弹。

> “未经优化的对冲会成为攻击自身的最精密的 DoS 工具。”

## Request Coalescing：效率最大化 vs. 命运共享（Fate Sharing）的深渊

### 单个请求的失败如何蔓延至数千个客户端

请求合并是通过将重复的请求合二为一，从而显著减轻后端负载的技术。它可以说是数据库查询或高成本计算中常见的效率巅峰。

然而，这里出现了一个可怕的概念——“命运共享（Fate Sharing）”。由于数千个请求都依赖于同一个处理过程，当这唯一的处理过程失败或延迟时，所有客户端都会同时受到打击。

为了效率而放弃个体请求独立性的代价比想象中要沉重。一个包含异常参数的请求可能会污染整个合并组，导致大范围的服务不可用。

![Hedged Requests - 表现了“单点故障”的概念：连接着数千根线的单一金色节点破碎，导致所有东西同时坍塌。](../../../../../source/posts/Hedged_Requests/a01d382b-1.webp)

### 试图规避 <a href="/cn/glossary/thundering-herd" class="glossary-tooltip" data-definition="当特定资源失效时，大量等待中的请求同时访问该资源，导致系统过载的现象。">Thundering Herd</a> 问题却遭遇单点故障（SPOF）风险

我们通常为了防止缓存在过期时涌入的惊群效应（Thundering Herd）而引入合并。我们期待它能作为一种保护后端系统的防线。

讽刺的是，这道防线本身也可能成为新的单点故障（SPOF）。如果管理合并的内存队列满了，或者管理逻辑发生瓶颈，整个系统将停止响应。

必须铭记的是，为了挤出性能而引入的复杂逻辑，反而会降低系统的可观测性，并在发生故障时增加定位原因的难度，成为一剂毒药。

> “合并的效率是以单点故障（SPOF）为代价换取的成果。”

## 必胜架构：比优化更重要的“风险控制”策略

### 熔断器与自适应节流的结合：失控的优化即灾难

真正的专家不仅会应用技术，还会设计预防技术失控的制动装置。对冲和合并都必须与控制装置相结合。

请通过下面的对比表，明确确认各项技术的特性以及我们需要控制的风险本质。

| 优化技术 | 核心目标 | 主要风险 (Operational Risk) | 资源消耗特性 | 推荐控制工具 |
| :--- | :--- | :--- | :--- | :--- |
| **Hedged Requests** | 减少尾部延迟 | Self-DoS（流量激增）、数据不一致 | CPU/网络带宽增加 | Istio VirtualService, hedge-fetch |
| **Request Coalescing** | 资源效率化 | Fate Sharing（故障蔓延）、产生 SPOF | 内存使用量（等待队列管理） | Python asyncio (singleflight) |

- **Google BigTable 案例研究**：引入对冲后，99.9% 的延迟从 1,800ms 缩短到 74ms，降幅达 95.8%，但总流量仅增加了约 2%。
- **阈值建议**：对冲延迟通常设定在 P95~P99 延迟之间时，能以最小成本获得最大效果。
- **技术栈关联性**：在设置 Istio 的推测性重试时，如果 `perTryTimeout` 过短，且在 Python `asyncio` 环境中对 `CancelledError` 处理不足，可能会产生大量僵尸进程（Zombie Task）。

为了实现有效的风险控制，必须通过熔断器快速传播失败，并通过自适应节流拦截超出系统承载能力的对冲请求。

盲目的优化只是工程师的虚荣心。基于准确反映系统当前状态的指标，思考在失败时如何优雅地停止，才是资深工程师应有的态度。

### 结论：技术成熟度取决于“失败模式分析”而非技术实现

在分布式系统中，不存在完美的优化。所有技术都是权衡（Trade-off）的产物，我们在获得性能的同时，也在支付可用性或复杂性的成本。

优秀的架构师在引入新技术时，比起该技术带来的优点，会先执着地挖掘它“将如何崩溃”。缺乏失败模式分析的优化，只是随时可能倒塌的沙堡。

请记住，技术成熟度并不体现在使用了多么华丽的技术栈，而在于是否明确认知系统的极限，并能多么稳定地对其进行控制。
