## 1. 为什么现在要重新讨论“循环依赖”？

### 1.1 Node.js 22 严格的模块加载：不再有“宽容”

 升级到 Node.js 22 后，许多工程师正面临以前从未见过的模块加载错误。事实上，在 Node.js 12 等较低版本中，即使发生循环依赖，系统也会默许访问部分加载的对象，从而勉强维持运行。

 然而，最新的运行时环境严格屏蔽了这些不完整的引用，并通过“Accessing non-existent property”等警告即刻暴露设计缺陷。这不仅仅是运行时的技术变化，更是生态系统发出的一个宏大信号，迫使开发者设计出更精细、更符合逻辑的模块结构。

### 1.2 Spring Boot 2.6+ 政策的启示：为什么“<a href="/cn/glossary/what-is-fail-fast" class="glossary-tooltip" data-definition="一种设计方式，当发现系统错误或缺陷时立即停止执行并报错，从而预先防止潜在副作用或更大故障的扩散。">Fail-Fast</a>”成为标准

 作为 Java 领域的标准，Spring Boot 也从 2.6 版本开始将 `spring.main.allow-circular-references=false` 作为默认设置，向循环依赖宣战。在应用程序启动阶段发现问题的“Fail-Fast”策略，是为了预先屏蔽服务运行过程中可能出现的不可预测 Bug 的必然选择。

 这种政策变化提醒我们，不应再放任错综复杂的依赖关系。架构重构不再是时间充裕时的可选任务，而是为了系统生存而必须立即执行的首要任务。

* **Node.js 各版本的变化**：在 v12 中，循环依赖时部分允许不完整的 export 访问，但在 v22 中，由于严格的模块加载机制，无法访问时会立即发出警告。
* **Spring Boot 政策数据**：从 2.6 版本开始，`spring.main.allow-circular-references` 选项的默认值更改为 `false`，发现循环依赖时将阻止应用程序启动。
* **架构改进指标**：引入接口分离和事件驱动架构时，模块间的直接依赖耦合度最多可降低 80% 以上。

## 2. 循环依赖：掩盖设计缺陷的“定时炸弹”

### 2.1 耦合度 (Coupling) 超过临界值：模块间边界崩溃的证据

 循环依赖的发生意味着单一职责原则 (SRP) 已遭到惨重破坏。两个模块深度参与彼此内部实现的状态，会使维护成本呈指数级增长，一次微小的代码修改都可能引发整个系统的多米诺骨牌效应。

 我们常以忙碌为借口忽视这些依赖关系，但这最终会导致架构灵活性的彻底丧失。模块边界模糊的系统只会退化为无法再扩展的“巨型泥潭”。

### 2.2 @Lazy 和延迟加载的风险：不是解决问题，而是“掩盖”问题

 现场常用的 `@Lazy` 注入或动态 `require()` 实际上更像是掩盖症状的镇痛剂，而非解决方案。这些权宜之计是非常危险的行为，它们将启动时的错误转移到了实际服务运行的运行时中。

 延迟加载只是暂时延缓了炸弹的计时器，并不能拆除炸弹本身。如果在流量激增的关键时刻，系统在意想不到的地方崩溃，那么责任将完全由放任设计的工程师承担。

## 3. 各技术栈的循环依赖问题及其对现场的即时影响

### 3.1 Java/Spring：破坏 Bean 生成生命周期并增加系统复杂度

 在 Spring 框架中，Bean 之间的循环依赖会阻碍作为面向对象核心的构造函数注入。这不仅破坏了对象的不变性，还会让编写测试代码变成一场噩梦。结果，无法测试的代码被大量生产，软件整体质量走下坡路。

### 3.2 Python：运行时导入错误对服务可用性的打击

 由于 Python 在执行模块时处理导入的特性，在复杂的循环依赖结构中很容易在部署后立即引发 `ImportError`。在微服务环境中，这种运行时错误会导致服务立即停机，给业务带来致命损失。

## 4. 逃离“架构破产”的 3 阶段根本处方

### 4.1 策略 1：接口分离 (ISP) 及提取公共模块

 切断直接依赖的第一步是将必要的最小规范提取为接口。应将相互依赖的功能转移到第三方的公共工具模块中，或者设立只定义规范的抽象层，使具体的实现类彼此互不相识。

### 4.2 策略 2：通过引入<a href="/cn/glossary/mediator-pattern" class="glossary-tooltip" data-definition="将对象间的直接交互封装在中心中介者对象中，从而降低模块间耦合度的设计模式。">中介者模式</a>消除直接依赖

 让两个模块不再直接对话，而是通过中介者 (Mediator) 进行通信，是一个非常聪明的策略。由于每个模块只关注中介者，循环链会自然解开，从而极大地降低对象间的耦合度。

### 4.3 策略 3：转向事件驱动通信 (Pub/Sub)

 最强大且最值得推荐的解决方案是完全消除依赖本身。不要让模块 A 直接调用模块 B，而是转向模块 A 发布特定事件，模块 B 订阅该事件的结构。这种异步通信方式彻底破坏了物理依赖链，将系统的扩展性提升到了极致。

> “循环依赖是预示系统智能崩溃的前兆，放任不管无异于自寻架构破产。”

> “@Lazy 只是暂时停止定时炸弹计时器的权宜之计。真正的工程师应追求拆除炸弹的设计，而非隐藏它。”

## 5. 结论：告别技术债，回归设计之本

 我们不能再将循环依赖仅仅视为简单的编码失误。因为它是一个诚实的指标，显示了我们的架构病得有多重。最新的技术环境不再容忍懒惰和平庸的设计。

 现在是时候果断舍弃权宜之计 `@Lazy`，通过接口分离和事件驱动通信等根本性解决方案找回系统的稳固性了。请记住，优秀的工程设计并非始于隐藏问题的能力，而是始于寻找并消除问题根源的勇气。
