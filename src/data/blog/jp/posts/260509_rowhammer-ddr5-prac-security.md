<div class="bluf"><strong>[BLUF]</strong><p>DDR5 は <a href="/jp/glossary/rowhammer" class="glossary-tooltip" data-definition="メモリチップの特定の行を繰り返しアクティブ化する際に発生する電磁干渉により、隣接するセルのデータを物理的に改ざんするハードウェアの脆弱性です。">Rowhammer</a> から安全であるという楽観論は、もはや有効ではありません。Phoenix 攻撃や GPUBreach はハードウェアレベルの防御機構を無力化しており、PRAC のような代替案も標準化の空白の中で実質的な脅威を完全に防ぎきれずにいます。パフォーマンスの低下を許容してでも、リフレッシュ周期（tREFI）を短縮するなどの即時的な実務対応が急務です。</p></div>

これまでハードウェアセキュリティ業界は、DDR5 の登場が Rowhammer（ロウヘマー）の脅威に終止符を打つものだと信じてきました。製造元がメモリ内部に搭載した Target Row Refresh（TRR）技術が、鉄壁の防御壁を形成してくれるという期待があったからです。

しかし、最近発表された一連の研究は、こうした信念がいかに危険な楽観論であったかを如実に物語っています。私たちは今、「ハードウェアは安全である」という盲目的な信頼から脱却し、より巧妙になった攻撃ベクトルを直視すべき局面に立たされています。

![Rowhammer - データエラーが発生した箇所がネオン色に輝く半導体ウェハーの近接写真です。](../../../../../source/posts/Rowhammer/647f00a3-0.webp)

2025 年のセキュリティエコシステムを揺るがした核心的な脅威の一つは、Phoenix（フェニックス）攻撃の登場です。この攻撃手法は、既存の TRR が採用しているサンプリングベースの防御ロジックの盲点を精密に突き、ビット反転（Bit-flip）を誘導します。

特に SK Hynix の DDR5 モジュール 15 種を対象に行われた全数テストの結果、すべてのモデルが Phoenix 攻撃に対して脆弱であることが明らかになりました。これは、製造元がブラックボックス形式で隠蔽してきたセキュリティ緩和策がいかに容易に崩れ去るかを象徴的に示しています。

> 「製造元の閉鎖的な防御戦略はセキュリティの不透明性を高めるだけであり、決して根本的な解決策にはなり得ません。今こそハードウェアセキュリティモデルを『信頼』から『検証』の領域へと移すべきです。」

攻撃の範囲は、システムのメインメモリだけにとどまりません。トロント大学の研究チームが発表した「GPUBreach」は、GPU の GDDR6 メモリも Rowhammer 攻撃から逃れられないことを立証しました。

GPU メモリの汚染は、単なるデータの改ざんを超え、システムのルート（Root）権限を奪取されかねない致命的な経路を提供します。これは、ハイパフォーマンスコンピューティング（HPC）や AI インフラを運用する Cloud プロバイダーにとって、これまでにないレベルの脅威となっています。

![Rowhammer - 暗い背景の中で砕けた水晶の破片の間から光が溢れ出し、情報の差異を抽象的に表現した様子です。](../../../../../source/posts/Rowhammer/3db7938d-1.webp)

このようなセキュリティの死角を解消するため、マイクロソフトは PRAC（Per-Row Activation Counting）という野心的な技術を提案しました。Project STEMA（Panopticon）技術に基づくこの方式は、DRAM 内で各行のアクティブ化回数を直接カウントし、攻撃を未然に遮断することを目指しています。

しかし、PRAC もまた、標準化プロセスにおける難航により、現場への適用には限界がある状況です。JEDEC 標準の空白と、製造元ごとの実装方式の差異は、攻撃者に別の回避経路を与える口実となっています。

| 攻撃手法 | 主な特徴および脅威対象 | セキュリティの死角 |
| :--- | :--- | :--- |
| **Phoenix** | SK Hynix DDR5 全モデルを回避 | TRR サンプリングロジックの死角を活用 |
| **GPUBreach** | NVIDIA GDDR6 ルート権限奪取 | GPU メモリアーキテクチャの防御欠如 |
| **PRAC** | MS 提案の DRAM 内カウント技術 | 未完成の標準化による相互運用性の欠如 |

私たちは今、ハードウェアセキュリティに対する視点を根本的に変える必要があります。CVE-2025-6202 識別子に代表される最新の脆弱性は、もはやソフトウェアパッチだけでは完全に解決できないという事実を警告しています。

実務的に最も確実な対応策は、パフォーマンスの低下を許容してでも、メモリのリフレッシュ周期（tREFI）を従来より 3 倍以上短縮することです。約 8.4% の性能損失が発生しますが、データの完全性とシステムの安定性を担保するためには、避けて通れない選択肢と言えるでしょう。

![Rowhammer - 金色のデータフローがデジタルセキュリティ網を突き抜けて進む、サイバーセキュリティの回復力を抽象的に表現した様子です。](../../../../../source/posts/Rowhammer/26e3b4b2-2.webp)

さらに、企業の CTO やセキュリティアーキテクトは、「Zero Trust」に基づくハードウェア検証体系を構築する必要があります。製造元の宣伝文句に依存するのではなく、独立したセキュリティ監査を通じて、自社ハードウェアの脆弱性を常時点検するプロセスが必要です。

スイス国立サイバーセキュリティセンター（NCSC）の責任ある開示プロセスのように、グローバルなセキュリティエコシステムとの緊密な協力も不可欠です。情報の非対称性を解消し、脅威情報をリアルタイムで共有してこそ、ハードウェアセキュリティの限界点を乗り越えることができるからです。

ハードウェアセキュリティは、静止した城壁ではなく、攻撃者と防御者が絶えず知恵を絞り合う動的な戦場です。DDR5 と PRAC が示した限界を教訓に、私たちはより堅牢で透明なセキュリティエコシステムを設計していかなければなりません。
