<div class="bluf"><strong>[BLUF]</strong><p>Kubernetes v1.36は高性能ワークロード向けの革新を提供しますが、gitRepoの強制削除とexternalIPsのサポート終了により、既存のレガシーシステムに破壊的なマイグレーションリスクをもたらします。運用者は単なる新機能の導入よりも、Alpha/Beta APIによる「設定過負荷（Configuration Overload）」問題の解決を最優先に考慮する必要があります。</p></div>

Kubernetesの新しいリリースv1.36「Haru」は、私たちに諸刃の剣のような課題を突きつけています。クラウドネイティブのエコシステムが成熟するにつれ、システムはより精緻になっていますが、その裏側では運用者が負担すべき複雑さの重みが指数関数的に増しています。単に新機能を羅列するだけでなく、今回のアップデートが実際のインフラアーキテクチャにどのような亀裂を生じさせているのか、冷静に見極めるべき時です。

## 1. 「空を飛ぶ」Haru、その背後に漂う複雑性

### 1.1. 新機能の約束：高性能ワークロードと精緻な制御

v1.36は、特に人工知能（AI）や機械学習（ML）のワークロードを収容するための強力な意志を表明しています。<a href="/jp/glossary/dra-dynamic-resource-allocation" class="glossary-tooltip" data-definition="GPUなどの特殊なハードウェアを柔軟に割り当てるためのKubernetesの新しいリソース割り当てフレームワークです。">DRA (Dynamic Resource Allocation)</a>の高度化は、従来の静的なリソース割り当て方式から脱却し、ハードウェアアクセラレータを柔軟に管理できる土台を築きました。これは高性能演算を必要とする企業にとって明らかな恩恵ですが、これを実装するために必要な複雑なAPI構造は、また別の障壁として立ちはだかります。

ポッドグループを一つの論理単位としてまとめて処理する<a href="/jp/glossary/was-workload-aware-scheduling" class="glossary-tooltip" data-definition="ポッドグループを一つの論理単位として認識し、アトミックにスケジューリングする高性能ワークロード最適化機能です。">WAS (Workload Aware Scheduling)</a>の導入も革新的です。分散環境で発生する部分的なスケジューリング問題を根本から解決し、全体的なリソース効率を最大化できます。しかし、このような「アトミックなスケーリング」はスケジューラー設定の難易度を飛躍的に上昇させ、運用者が考慮すべき変数を大幅に増やす結果を招きました。

### 1.2. しかし現実は？Alpha/Beta APIがもたらす運用の影

革新的な機能の大部分がまだAlphaまたはBeta段階に留まっているという点は、現場の運用者にとって大きな負担です。未成熟なAPIはいつでも下位互換性を無視して変更される可能性があり、それはすなわち運用環境における不安定さに直結します。機能を使用するために有効化する必要がある数多くの<a href="/jp/glossary/what-is-feature-gate" class="glossary-tooltip" data-definition="Kubernetesクラスターで特定の機能の有効化・無効化を個別に制御するために使用される設定メカニズムです。">フィーチャーゲート</a>（Feature Gates）は、いわゆる「設定過負荷」を引き起こし、ヒューマンエラーの発生可能性を高める主要因となっています。

## 2. 主要アップデート分析：バラ色の機能と隠された複雑性

今回のリリースの核心内容を以下の表で一目で確認してください。各機能のステータスと、それに伴うリスクを明確に認識することが、成功するマイグレーションの第一歩です。

| カテゴリ | 機能名 | ステータス | 主な影響とリスク |
| :--- | :--- | :--- | :--- |
| **セキュリティ** | Kubelet Fine-grained Authz | Stable | 権限の最小化が実現可能だが、RBAC設定の複雑さが増大 |
| **スケジューリング** | Workload Aware Scheduling (WAS) | Alpha | 高性能ポッドグループのアトミック配置が可能、設定過負荷を誘発 |
| **ストレージ** | gitRepo Volume Driver | Removed | 既存ワークロードの中断が発生、即時のマイグレーションが必須 |
| **ネットワーク** | Service.spec.externalIPs | Deprecated | CVE-2020-8554のセキュリティリスク排除、v1.43で完全削除予定 |

### 2.1. Stable機能：安定性の確保と共に訪れた新しい管理ポイント

Kubelet Fine-grained AuthorizationがStable段階に進んだことは、セキュリティ面で大きな前進です。従来Kubeletに付与されていた包括的な権限を細かく制御できるようになることで、内部の脅威からクラスターを保護できるようになりました。しかし、細かな制御はすなわち管理すべきRBACポリシーが増えることを意味し、これは大規模クラスターを運用する組織にとって設定管理の疲弊を加速させます。

### 2.2. Beta機能：有用だが、まだ課題の多い機能

Beta段階の機能は、機能的な完成度は高いものの、運用のガイドラインが明確に確立されていないケースが多いです。特にネットワークとストレージインターフェースの拡張は、クラウドプロバイダー（CSP）との緊密な統合を要求します。これはベンダーロックインを深める懸念があり、マルチクラウド戦略を推進する企業にとっては追加のアーキテクチャ検討を強いる要素でもあります。

### 2.3. Alpha機能：未来を垣間見る、しかし「設定過負荷」の頂点

Alpha段階で提供される機能は、実質的に「諸刃の剣」です。最新技術を先制的に導入して競争力を確保できるという利点がありますが、運用環境に適用するにはリスクが大きすぎます。WASのような機能は特にスケジューリングロジックを複雑にし、トラブルシューティングの難易度を指数関数的に高めます。専門家は、このようなAlpha機能の無差別な導入がシステム全体の観測性を損なう可能性があると警告しています。

> 「v1.36は『設定過負荷』の時代を告げ、運用者により精緻な統制力と同時に、重い管理責任を課している。」

## 3. 現場の足を引っ張る「破壊的マイグレーション」リスク

### 3.1. Service.spec.externalIPs Deprecation：セキュリティ負債の清算開始

長期間放置されていた `externalIPs` のセキュリティ上の欠陥が、ついに本格的な規制段階に入りました。CVE-2020-8554として知られるこの脆弱性は、攻撃者がトラフィックを傍受できる致命的な穴でした。v1.36からはこの機能の使用が厳格に制限され、将来のv1.43では完全に削除される予定です。従来のレガシーインフラで依然としてこの方式を使用しているケースが多く、Gateway APIへの移行はもはや先送りできない生存の問題となりました。

### 3.2. gitRepo Volume Driver 強制削除：レガシー清算と即時対応

さらに深刻な問題は、`gitRepo` ボリュームドライバーの永久削除です。ノードのroot権限を利用して悪意のあるコードを実行できる潜在的なリスクを排除するための措置ですが、これを利用してきた古いデプロイパイプラインは即座に停止する危機に瀕しています。運用チームは今すぐinitコンテナを構成するか、`git-sync` のようなサイドカーパターンでアーキテクチャを完全に再設計する必要があります。これは単なるバージョンアップグレードを超え、サービス運用の継続性を脅かす破壊的な変化です。

## 4. 結論：Kubernetes v1.36、賢明なアップグレードのためのチェックポイント

Kubernetes v1.36「Haru」は、私たちに技術的な進歩とともに、運用の成熟度を問う質問を投げかけています。華やかな新技術に目を奪われるのではなく、私たちが抱えているセキュリティ負債とレガシーの重みをまず測定すべきです。今回のリリースの数値的な成果は以下の通りです。

* リリース周期：2026年1月12日から4月22日までの15週間
* 寄与規模：106社が参加、491人の個人コントリビューターが70の機能強化を完了
* 機能分布：18の機能がStableに移行、25の機能がBeta/Alphaに参入
* 市場の特異点：金融およびEC業界を中心にexternalIPsの使用事例が報告されており、Gateway APIの導入が加速

> 「セキュリティ負債を解決するためのgitRepoの永久削除は、選択ではなく生存のための強制的な転換点である。」

結局、成功するv1.36運用の核心は「単純化」にあります。新機能が提供する誘惑に打ち勝ち、クラスターの複雑さを統制可能なレベルに維持しながら、セキュリティ上の脅威となるレガシーを迅速に取り除くこと。それこそが、今の時代のKubernetesアーキテクトに求められる真の能力といえるでしょう。
